# Camera standard: proposal (2026-09-02)

A proposal for one folder layout, one plain-English pipeline with a **setup**
mode and a **live** mode, one device↔server contract, and a recipe an LLM can
follow to write the software for any new camera. Phase 0 (docs) is done; see §10.

Contents: 1 findings · 2 the standard · 3 the pipeline in plain English ·
4 modes · 5 contract · 6 configuration · 7 folder layout · 8 the recipe ·
9 phased plan · 10 decisions (taken).

---

## 1. What exists today (findings)

Five camera directories, four runtimes, three upload protocols, two OTA
directions, no shared code.

| Camera | Runtime | Power model | Trigger | Upload | Telemetry | Config | OTA | Setup mode | State |
|---|---|---|---|---|---|---|---|---|---|
| openmv_rt1062 | MicroPython 4.8.1 (`sensor` API) | always on | VGA diff + heartbeat | blob gate, `X-Meta`, token, TLS-capable | HTTP `/telemetry` → MQTT | `gen_secrets.py` from `~/.dusty`, tuning stamped into app | push (board HTTP :8266) with rollback | focus page :8267, button, watchdog page | **live** |
| openmv_n6 | MicroPython 5.0 (legacy `sensor` API) | always on, or LP variant (WiFi off between deliveries) | VGA diff + heartbeat | ingest direct, no token | direct MQTT (ACL-limited) | hand-copied `secrets.py` | push | none (USB preview only) | built, silent since 08-20 |
| esp32_s3_cam / camlogger | ESP-IDF C | deep-sleep wake cycle | RTC thumbnail diff + TFLite animal gate + heartbeat | ingest direct, `X-Meta` (different keys) | none (rides in meta) | `sdkconfig.secrets` compiled in; runtime `GET /config/<device>` | pull `/firmware/<name>` with bootloader rollback | recovery / debug / capture modes via button + server config | built, silent since 08-18; **build path broken** |
| esp32_s3_cam / MicroPython + persondet | MicroPython; ESP-IDF | always on | interval; free-running | `/upload`; `/sample` raw gray | none | `secrets.py` | none; pull | safe-mode shim | abandoned tracks |
| pi5cam | CPython node graph | always on (mains/solar) | motion (OpenCV) | **none** (files on SD) | none | hardcoded | git pull by hand | web dashboard :8000 (unauthenticated) | prototype; deployed unit runs a broken test file |
| n6_speedcam | MicroPython 5.0 | deep sleep + radar wake | radar pass | unwritten | unwritten | constants | — | `SLEEP` constant | designed, unbuilt |

Things every camera got right somewhere, which the standard keeps:

- **Meta on frames** (`ts, w, h, diff, heartbeat, buffered, v, ip`) and
  `meta.ts` as the authoritative timestamp (rt1062, n6, camlogger).
- **Spool-and-drain** offline buffering with sidecar-first writes (rt1062, n6, camlogger's SD).
- **Heartbeat as the safety net**: a frame every N minutes regardless of motion
  keeps the device reachable for config and OTA (all three deployed boards).
- **Recovery mode that is never updated OTA** (`ota_main.py`; camlogger's BOOT-held loop; MicroPython safe-mode shim).
- **Server-pulled runtime config** (`GET /config/<device>`, camlogger).
- **Tuning shipped separately from credentials** (rt1062's stamped `TUNING`).
- **Cheap preview + expensive capture** (rt1062's VGA diff / full-res JPEG; pi5cam's lores/still switch).
- A **live preview with a sharpness score** for focusing (rt1062 focus mode).

Things the standard must fix:

- Three incompatible meta vocabularies (`why`/`seq`/`animal_pct` vs `diff`/`gate` vs nothing).
- Two OTA directions; the push model needs the board's LAN IP and cannot work through the Funnel or for sleeping boards.
- `secrets.py`/`sdkconfig.secrets` are hand-built or generated by a tool that no longer exists (`dusty generate`).
- ~200 lines duplicated between rt1062, n6 and n6-lp because the OTA channel installs exactly one file.
- No camera has a **mode** concept that a server or a phone can see; only rt1062 reports one.
- `docs/openmv_n6_protocol.md` is the OpenMV IDE wire protocol, not our device protocol. No document states the device↔server contract; it lives in code.
- The blob gate proxies only `POST /blob` and `POST /telemetry`; remote boards cannot pull config or firmware.

## 2. The standard in one paragraph

A camera is a device that runs **one loop** in one of two modes. In **live**
mode it watches cheaply, captures when triggered, judges, records a frame
plus a standard meta JSON, delivers it to sensorhub or spools it, reports
telemetry on a fixed cadence, and always keeps its control plane reachable.
In **setup** mode it stops recording and instead streams a live preview with
a focus score, takes manual shots, and reflects new configuration, then
returns to live mode by itself. Configuration has three tiers (identity and
credentials; tuning; board facts), and only tuning changes after flashing.
Every camera speaks the same contract to sensorhub, lives in the same folder
layout, and states in its README which pipeline stages it implements and
which it does not.

## 3. The pipeline in plain English

Written so it holds for an always-on MicroPython board, a deep-sleep
ESP-IDF board, and a Raspberry Pi. A stage that a board cannot do is stated
as "not applicable" in that camera's README, never silently skipped.

**Boot.** Load identity and credentials from the secrets file. Load tuning:
the defaults stamped into the firmware, overridden by the last configuration
pulled from the server (kept in non-volatile storage). Check for a recovery
request: user button held, or a flag file, or the previous app crashed with
nothing to roll back to. Recovery mode is a tiny program that only serves
the control plane and is never updated over the air.

**Connect.** Join WiFi (or the radio the board has). Sync the clock. Note
the board's IP address; it goes into every meta and every telemetry report.
Failure to connect is not fatal: the loop runs and spools.

**Announce.** Send one telemetry report with the firmware version, config
version, mode, uptime zero, and the reason for booting.

**Then loop:**

1. **Sense.** Read the sensors the camera has (radar, battery, charge state,
   IMU, temperature). Sensor readings are numbers with stable names.
2. **Watch.** Take a cheap preview frame (small, grayscale or RGB565) and
   evaluate the trigger: motion (difference against the last *recorded*
   frame), a sensor event (radar pass, PIR), an interval, a manual request
   from setup mode, or the heartbeat timer. Every trigger has a name (`why`).
3. **Capture.** Take the real frame at the quality the camera is configured
   for (full sensor resolution, sensor-side JPEG when the sensor can). Note
   the width, height and byte size.
4. **Judge.** Optionally run an on-device model on the frame or the preview
   (animal gate, person detector). The result is a list of detections with
   label and confidence, and a decision: keep, discard, or keep-as-audit
   (one in N discarded frames still sent so the gate can be checked).
5. **Record.** Build the meta JSON with the standard keys (section 5) plus
   the camera's own sensor fields. Build the telemetry dict from counters and
   sensor readings.
6. **Deliver.** Upload the frame and meta to sensorhub. If the server is
   unreachable, spool the frame and its meta sidecar to local storage
   (sidecar first, then the image, then rename). When an upload succeeds
   again, pause recording and drain the spool oldest-first, then resume.
   Delivery is at-least-once; the server de-duplicates on `ts`.
7. **Report.** On a fixed cadence (`telemetry_s`), send the telemetry dict.
   Numbers only. It includes counters (sent, skipped, failed, pending), health
   (memory, RSSI, uptime, battery), and the current mode.
8. **Serve.** Service the control plane: answer status, accept a mode change,
   accept a config refresh, check for or accept a firmware update. On an
   always-on board this is a non-blocking poll from *every* place the loop
   spends time (including mid-drain). On a wake-cycle board it happens once
   per contact, right after a successful upload. Nothing in the loop may
   block the control plane for more than a few seconds.
9. **Rest.** Always-on boards idle until the next period, keeping the
   preview stream fresh. Wake-cycle boards persist their state (last
   thumbnail, counters, config) and deep-sleep until the next wake or sensor
   interrupt.

**Rules that apply to every stage (the laws):**

- The heartbeat frame is the safety net. It is the only guarantee that a
  board with a bad config or a broken gate stays reachable.
- Firmware first, then config. Never ship a config value the running
  firmware does not understand.
- `meta.ts` is the truth. `meta.ip` is always present. `meta.v` is the
  firmware version. `why` says what triggered the frame.
- A failed publish must be visible. Telemetry goes over HTTP to the gate
  (which answers), not directly to MQTT (which drops silently on an ACL miss).
- Nothing that talks TLS runs while a viewer is attached to the preview.
- The spool never fills the storage: a cap on pending files, oldest sent
  reclaimed first.
- Board-health calls that are known to hang the MCU (N6 core temperature,
  cpufreq while streaming) are on a per-board deny list in board facts.
- Every long-running host tool retries serial glitches; every deploy script
  refuses to run if the board is not the one it expects.

## 4. Modes

Three modes. Only two are the camera's business.

| Mode | What runs | Entered by | Left by |
|---|---|---|---|
| **live** | the loop of section 3 | boot (default); leaving setup | entering setup; crash → recovery |
| **setup** | preview stream with focus score; manual shots; config refresh; sensor readouts; control plane | user button held ≥1 s; `GET /setup` on the board; server config `mode: setup` picked up at the next contact | timeout (`setup_secs`, default 300); `GET /live`; button again; server config back to `live` |
| **recovery** | control plane only | app crash with nothing to roll back to; button held at boot | a successful firmware update |

**What setup mode offers (the phone page):**

- A live preview (grayscale, small, ~5-10 fps) with the sharpness score of a
  centre region, the session's best score, and the seconds remaining. The
  page polls the board's status and reopens the stream if frames stop.
- A **shoot** button: capture and deliver one full-quality frame now
  (`why: manual`), so the result can be checked in sensorhub at full size.
- Live sensor readouts (radar speed, battery volts, RSSI) refreshed with the
  status poll, so a radar can be aimed and a solar panel checked in place.
- The current tuning and config version, and a **refresh config** button that
  makes the board pull `/config/<device>` now.
- Links to the device's sensorhub page and to its firmware version.

**What setup mode does not do:** edit values on the board. Configuration is
edited on the workstation (`~/.dusty/config.toml`) and published to the
server; the board pulls it. One source of truth, no per-board forms.

**Behaviour while in setup:** recording is paused, the heartbeat timer is
held, telemetry continues with `mode=1` but only while no viewer is
attached, OTA stays reachable, the LED shows the mode. On exit the motion
reference is reset and one confirmation frame is delivered.

**Wake-cycle boards:** setup mode means "stay awake for `setup_secs` after
this contact and serve the page" — camlogger's capture mode generalised.
Deep sleep resumes when the mode ends.

**Raspberry Pi:** setup mode is the same page served by the same service;
the preview comes from the pipeline's preview branch.

## 5. The contract (device ↔ sensorhub)

One contract for every board. Where a board already does this, it stays;
where it differs, it migrates.

**Identity.** `device` is a short lowercase id (`rt1062cam`, `n6cam`,
`goouuu1`, `speedcam1`). It names the blob path, the telemetry topic prefix,
the config file, the firmware artifact, and the `devices.json` entry.

**Frames.** `POST /blob/<device>/frame`, `Content-Type: image/jpeg`, body =
the image, header `X-Meta` = JSON. Through the gate (`:8089` on the LAN,
Funnel `:10000`, `X-Token`) by default; ingest `:8088` direct is a LAN-only
fallback.

Standard meta keys, all boards:

| key | meaning |
|---|---|
| `ts` | capture time, epoch seconds (authoritative) |
| `seq` | monotonic per boot |
| `w`, `h` | pixels |
| `v` | firmware/app version string |
| `cfg` | config version the board is running |
| `ip` | board IP |
| `mode` | `live` / `setup` / `recovery` |
| `why` | `motion` / `heartbeat` / `sensor` / `interval` / `manual` / `audit` / `burst` / `boot` |
| `diff` | motion fraction that fired (or 0) |
| `gate` | the threshold in force |
| `heartbeat`, `buffered` | booleans (kept for the existing analyzer and pages) |
| `det` | optional on-device detections `[{"label":…, "conf":…}]` |
| camera-specific | prefixed with the sensor name: `radar_kmh`, `radar_dir`, `batt_v`, `lum`, `exp` |

Reserved for the server: `detected`, `animals`, `detections` (the analyzer
merges these in). Boards never write them.

**Telemetry.** `POST /telemetry/<device>` JSON object of numbers; the gate
republishes each key as MQTT `<device>/<key>`. Standard keys: `uptime_s`,
`mem_free`, `rssi`, `frames_sent`, `frames_skipped`, `upload_failures`,
`pending_files`, `mode` (0 live, 1 setup, 2 recovery), `cfg`, `boot_count`,
plus `batt_v`, `charging`, and sensor readings by name. Cadence `telemetry_s`.

**Config pull.** `GET /config/<device>` returns JSON of tuning keys and
`cfg` (a version number). The board applies known keys, ignores unknown
ones, stores the result, and reports `cfg` in meta and telemetry. Pulled at
boot, after every successful upload on wake-cycle boards, and every
`config_s` (default = heartbeat) on always-on boards.

**Firmware.** Pull model as the standard: `GET /firmware/<device>/version`,
compare, `GET /firmware/<device>.py|.bin`, verify (compile check for
MicroPython, image validation for ESP-IDF), install with rollback (previous
copy kept; must complete one successful upload before it is marked good).
Checked on every config pull. Staging = copy the artifact and a `.version`
file into `/hd2/sensorhub/firmware/`. The OpenMV push path (`ota_push.py`)
remains as a developer fast path, not as the standard.

**Control plane on the board** (always-on boards): one HTTP listener, one
port (`8266`): `GET /status` (open), `GET /setup`, `GET /live`, `GET /stream`,
`POST /shoot`, `POST /refresh`, `POST /update` (push OTA, token). The
current split across :8266 and :8267 merges.

**Server-side changes this needs:** the gate proxies `GET /config/<device>`
and `GET /firmware/<device>[/version|.py|.bin]` (token-checked) so remote
boards can pull; `devices.json` gets `expect` for every camera; the device
page shows `mode` and links to the board's setup page when it is on the LAN.

## 6. Configuration: three tiers

| Tier | Examples | Lives in | Reaches the board by | Changes after flashing? |
|---|---|---|---|---|
| **identity + credentials** | device id, WiFi, server host/ports, tokens, MQTT creds | `~/.dusty/secrets.toml` + `[server]` in `config.toml` | generated secrets file, flashed over USB (or compiled in) | no |
| **tuning** | period, diff threshold, heartbeat, telemetry cadence, capture size, setup secs, gate pct, wake interval, mode | `~/.dusty/config.toml` `[camera.<name>]` | stamped into the firmware as defaults **and** published to `/data/config/<device>.json` for pull | yes, without reflash |
| **board facts** | pins, sensor, framesize names, LED/button names, deny-listed calls | the board adapter in the camera's software | with the firmware | with the firmware |

One generator replaces the removed `dusty generate`: `tools/dustygen
<camera>` reads `~/.dusty` and the camera's manifest and writes the secrets
file in the board's format (`secrets.py`, `sdkconfig.secrets`, `.env`),
stamps the tuning defaults, and writes the server config file. `--public`
selects the Funnel host/port and TLS. Tuning edits become: edit
`config.toml`, run `dustygen`, done (the board pulls it at its next contact).

## 7. Folder layout

```
cameras/<camera>/
  README.md            what it is, board facts, deploy, status line, and a
                       "Standard mapping" section: one line per pipeline stage
                       saying how this camera does it or "not applicable: why"
  camera.toml          manifest (below)
  hardware/            case, carrier, power, optics: sources + exports, README
  software/
    app/               what runs on the board (one app; power model is a setting,
                       not a second file)
    host/              workstation tools: deploy, stage-firmware, bench, preview
  tests/               host-runnable pytest: parsers, motion math, meta builders,
                       config merge. No board needed.
```

`camera.toml` manifest (small, machine-readable; drives the generator, the
README table, and the recipe's checklist):

```toml
id = "rt1062cam"
board = "OpenMV Cam RT1062 R6"
runtime = "micropython"        # micropython | espidf | cpython
power = "always_on"            # always_on | wake_cycle
status = "live"                # designed | built | live | archived
sensors = ["battery", "charge"]
capabilities = ["preview", "focus_score", "motion", "full_res", "spool", "pull_config", "pull_firmware", "push_firmware", "setup_mode"]
[tuning]                       # defaults; keys also allowed in config.toml
period_s = 10
diff_min_frac = 0.04
heartbeat_s = 300
telemetry_s = 60
setup_secs = 300
```

Shared code lives in `cameras/common/` with one subdirectory per runtime:

- `common/micropython/`: `uplink.py` (raw-socket POST, gate/ingest, TLS),
  `spool.py`, `telemetry.py`, `control.py` (status/setup/stream listener),
  `motion.py`, `focus.py`, `otapull.py`, `config.py`. Plus `bundle.py`,
  which inlines the modules a camera lists into a single `app.py` at build
  time, because the OTA channel installs one file. Tests run on the modules.
- `common/espidf/components/`: `dusty_uplink`, `dusty_spool`, `dusty_config`,
  `dusty_ota` as ESP-IDF components; the camlogger becomes a thin `main.c`.
- `common/cpython/dusty/`: the same stages as a package for the Pi.

Repo-level moves: `docs/openmv_n6_protocol.md` → `docs/openmv_ide_protocol_v2.md`
(it is the IDE wire protocol); `docs/camera_standard.md` and
`docs/camera_recipe.md` become the split-out, final versions of sections 3-8
of this file; the empty `dusty/` directory goes; `pyproject.toml` stops
pointing at one camera.

## 8. The recipe (text for an LLM writing a new camera)

This is the draft of `docs/camera_recipe.md`. It assumes the standard above
is in place. It is written to be pasted into a session as the task brief.

> **You are writing the software for a new dustycam camera.** Read
> `docs/camera_standard.md` first; it defines the pipeline, the modes, the
> contract with sensorhub, the configuration tiers and the folder layout.
> Then follow these steps in order. Do not skip a step; if a step does not
> apply, write why in the README's "Standard mapping" section.
>
> **1. Establish the facts before writing code.** Query sarg for the board,
> its sensor, its firmware version, and every part in the design. Read the
> closest existing camera (same runtime) and its README. Write
> `camera.toml`: id, board, runtime, power model, sensors, capabilities.
> Record the board facts you will need: pins for the button and LED, the
> camera framesize and pixel-format names, memory budget (frame buffer,
> heap), storage (SD or flash), radios, and any calls known to hang the
> board. Put unknowns in a list and resolve them on the bench before step 4.
>
> **2. Decide the trigger and the power model.** Always-on with motion diff,
> or wake-cycle with a sensor interrupt or an interval. State the expected
> frame rate to the server and the expected daily energy. If there is an
> on-device model, name its input size and where its weights live.
>
> **3. Lay out the folder** exactly as the standard says. Copy nothing from
> another camera's app; import from `cameras/common/<runtime>/` instead and
> list the modules in `camera.toml`. Write the README skeleton with the
> "Standard mapping" table filled in with your intentions.
>
> **4. Implement live mode stage by stage**, in this order, testing each on
> the bench before the next: Boot (secrets + tuning + recovery check) →
> Connect (WiFi, NTP, IP) → Deliver (one hard-coded frame reaches sensorhub
> with the standard meta) → Report (telemetry appears on the device page) →
> Serve (status endpoint answers; config pull works; firmware pull works with
> rollback) → Watch (preview + trigger with `why`) → Capture (full quality)
> → Judge (model, if any, with audit frames) → Record (spool + drain, verify
> by unplugging the network) → Rest (idle loop keeps the control plane
> responsive; or deep sleep with state persisted).
>
> **5. Implement setup mode**: button entry, `/setup` entry, server config
> entry; the preview stream with the focus score; `/shoot`; the phone page
> with its watchdog; timeout back to live; LED. Verify from a phone on the
> LAN that the page reconnects after the screen locks.
>
> **6. Write the host tools**: `dustygen` support for this camera's secrets
> format if it is new, a `stage-firmware` target, a bench script that prints
> the board's status. Add the device to `devices.json` with `expect`.
>
> **7. Write host tests** for every piece of pure logic (parsers, trigger
> math, meta builder, config merge, spool naming). They must pass without a
> board.
>
> **8. Prove it in the field**: one full day of live mode with a heartbeat
> every 5 minutes, then a config change pulled without reflash, then a
> firmware update with a deliberate bad build that rolls back. Record what
> you learned in sarg. Update the README status line.
>
> **Laws** (from the standard): heartbeat is the safety net; firmware before
> config; `ts`, `ip`, `v`, `why` in every meta; telemetry over the gate, not
> raw MQTT; no TLS while a viewer is attached; spool is capped; the control
> plane is polled from everywhere the loop waits; recovery mode is never
> updated over the air.

## 9. Phased plan

Each phase leaves every live camera working. The RT1062 is live now; it is
touched only through its existing OTA path with rollback.

**Phase 0 — write the standard (docs only).** Split sections 3-8 into
`docs/camera_standard.md` and `docs/camera_recipe.md`; rename the IDE
protocol doc; add `camera.toml` to each camera with today's truth (including
`status`); add "Standard mapping" tables to each README stating the current
gaps. Output: every camera's deviations are listed, nothing changes on any
board.

**Phase 1 — server side.** Gate proxies `GET /config` and `GET /firmware`
with the token; `devices.json` `expect` for every camera; device page shows
`mode` and a setup link. Output: remote boards can pull config and firmware.

**Phase 2 — `tools/dustygen` + `cameras/common/micropython/`.** Build the
generator from the rt1062's `gen_secrets.py`; extract the rt1062 app into
the common modules plus `bundle.py`; the bundled `app.py` must be
byte-for-byte equivalent in behaviour (same meta, same endpoints). Add
`seq`, `cfg`, `mode`, `why` to meta, config pull, firmware pull, merge the
two control ports, add `/shoot`. Ship to the RT1062 over OTA. Output: the
reference implementation of the standard is the live camera.

**Phase 3 — openmv_n6 onto the common modules.** Needs the N6 on the desk
(silent since 08-20). The LP variant becomes `power = "wake_cycle"`-style
settings (WiFi off between deliveries) rather than a second file. Telemetry
moves to the gate; `secrets.py` comes from `dustygen`. Battery divider
measured, not guessed. Output: one app for both N6 modes, no duplicate code.

**Phase 4 — esp32_s3_cam → camlogger only.** Fix the Docker build path,
move the MicroPython and persondet tracks to `archive/`, split the Waveshare
board out of the directory or drop it, align the meta keys with the
standard (`why` stays; `seq`, `cfg`, `mode` added), make `dustygen` write
`sdkconfig.secrets`, generalise capture mode into setup mode with the page.
Output: the wake-cycle reference implementation.

**Phase 5 — n6_speedcam built from the recipe.** The first camera written
by following `camera_recipe.md` end to end; its friction is the recipe's
test. Output: a validated recipe and a working speed camera.

**Phase 6 — pi5cam: decide and do.** Either implement the standard in
`common/cpython/dusty/` (real service entry point, upload to the gate, the
preview branch as setup mode, TFLite on the Pi) or mark it `archived` and
keep only the hardware notes. Recommendation: implement, because the
one-shot workflow targets the Pi; but it is the largest job and depends on
nothing else, so it goes last.

Rough sizes: phase 0 half a day; 1 half a day; 2 two days; 3 one day with
the board present; 4 two days; 5 two to three days plus the build; 6 three
days.

## 10. Decisions (taken 2026-09-02)

1. **Firmware:** pull is the standard for every board; the OpenMV push path stays as a developer fast path on the LAN.
2. **Control plane:** one port per board (`:8266`), GETs and setup endpoints open on the LAN, token only on `POST /update`. The RT1062's `:8267` merges in phase 2.
3. **Config editing:** workstation only (`~/.dusty/config.toml` → `dustygen` → server → board pull). The setup page shows values and refreshes; it edits nothing.
4. **pi5cam:** left as is. Work on it only with the device plugged in; its README carries the ordered list of what to do then.
5. **esp32_s3_cam:** camlogger (GOOUUU) only; the MicroPython logger and persondet_app move to `archive/` in phase 4; fix the Docker build path first.
6. **Sensors:** cameras now, sensors later. The standard is written device-generic (Watch/Capture/Judge optional) so the sensors directory can follow once the recipe is proven.

Phases 1–3 done 2026-09-03: gate GET proxies; `cameras/common/micropython/` + `tools/dustygen`; RT1062 (2.0.8-rt) and N6 (2.0.9-n6) both on the shared runtime with config pull, pull OTA and rollback proven on each; the N6 low-power variant became the `wifi_linger_s` setting. Left for the N6: button check, battery divider, a day of heartbeats.

Phase 0 was done the same day: `docs/camera_standard.md`, `docs/camera_recipe.md`, `camera.toml` in every camera, "Standard mapping" README sections, the IDE protocol doc renamed, the empty `dusty/` directory removed.

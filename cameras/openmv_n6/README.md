# openmv_n6

An **OpenMV N6** (STM32N657) camera on the shared MicroPython runtime of
[`docs/camera_standard.md`](../../docs/camera_standard.md): motion diff at
VGA, recorded frames as 1280x800 JPEGs (the sensor's native size; RGB565
capture + software JPEG, the CSI has no JPEG output), delivered through
sensorhub's blob gate, telemetry over the same gate, config and firmware
pulled from sensorhub, a setup mode with a phone page, one control port.
Board serial `31001c00025043364d343000`, firmware 5.0.0 / MicroPython 1.28
(v1.28.0-49). Second N6 (`004C347E3643`) not yet migrated.

**Status: live** (app 2.0.9-n6, 2026-09-03), reporting as `n6cam`:
http://192.168.86.26:8088/d/n6cam. No SD card (`sd: false`), so the spool
is inactive and frames that fail to upload are counted in `failed` and lost.
Setup page: http://192.168.86.211:8266/setup (LAN address changes with DHCP;
the device page's **setup** link follows `ip` in the meta).

Low power is a setting, not a second file: `wifi_linger_s > 0` in
`~/.dusty/config.toml` turns the radio off between contacts (see below).

## Deploy

Everything starts from `~/.dusty/config.toml` `[camera.openmv_n6]` and
`~/.dusty/secrets.toml`:

```bash
tools/dustygen cameras/openmv_n6 --stage        # LAN gate (add --public for the Funnel)
curl -X POST http://<camera ip>:8266/refresh    # or wait for the next heartbeat
```

writes `software/app/secrets.py`, stamps `TUNING` into `board.py`, publishes
the tuning to `/hd2/sensorhub/config/n6cam.json` (bumping `cfg` when it
changed), bundles `software/build/app.py`, and stages it as
`/hd2/sensorhub/firmware/n6cam.py` + `.version`. The board pulls a new `cfg`
at boot, every `heartbeat_s`, and on refresh; it pulls firmware whose
`.version` differs from its `APP_VERSION` and is not blacklisted, keeps
`app_prev.py`, and marks the install good after its first successful upload.
A build that crashes at import is rolled back by the loader and blacklisted
in `/flash/fw_bad.txt`. **Bump `APP_VERSION`** in `board.py` for every
staged build.

### First deploy (USB)

The board mounts as `/media/wroscoe/PYBFLASH` and enumerates as
`/dev/serial/by-id/usb-MicroPython_Pyboard_Virtual_Comm_Port_in_FS_Mode_31001c00025043364d343000-if00`.

```bash
D=/media/wroscoe/PYBFLASH; A=software/app
cp $A/secrets.py $D/secrets.py; cp $A/ota.py $D/ota.py; cp $A/ota_main.py $D/main.py
cp software/build/app.py $D/app.py; sync
udisksctl unmount -b /dev/sdX          # whichever PYBFLASH is; the board re-enumerates on reset
mpremote connect /dev/serial/by-id/usb-MicroPython_Pyboard*-if00 reset
```

Unmount before any reset (OTA install, rollback test): the host's mounted
FAT and the board writing `/flash` at the same time is the classic way to
corrupt it.

## Control port (:8266)

Same surface as the RT1062: `GET /status`, `GET /setup` (phone page),
`GET /stream?secs=N`, `GET /live`, `POST /shoot`, `POST /refresh`,
`POST /update` (push OTA, `x-token`). Requests during a full-res upload wait
a second or two; the live loop polls the port every 100 ms otherwise.

## Setup mode

Enter: the setup page, the user button `SW` (hold 300 ms; blue LED while
active), or `mode = "setup"` in the server config. Leave: `setup_secs`
timeout (240 s here), `/live`, the button, closing the page (30 s grace),
or the config flipping back. The stream is grayscale VGA (640x400 on this
sensor) at ~33 fps to a client that keeps up; the score is the stdev of a
x4 Laplacian over the boxed centre ROI, computed from the histogram
(daytime ceiling read 4.4–4.6; judge by the peak in daylight). With the
radio cycling (`wifi_linger_s`), the button brings WiFi up first.

## Low power (`wifi_linger_s`)

`wifi_linger_s = 20` with `period_s = 60` is the old `sensorhub_cam_lp.py`:
the radio goes off `wifi_linger_s` after the last contact (delivery,
telemetry, config pull, any control request) and comes back for the next
motion frame, heartbeat, or button press; telemetry is batched into each
window; config and firmware pulls happen only inside a window. The board is
unreachable between windows, so the heartbeat is the access cadence. Proven
2026-09-03 with linger 20 / heartbeat 60: off 20 s after each upload, back
for every heartbeat and motion frame, no failed uploads. Not done: sensor
frame-rate reduction and `cpufreq` (deny-listed until proven near USB).

## Standard mapping (docs/camera_standard.md, 2026-09-03)

| Stage / feature | How |
|---|---|
| Boot | `fw_boot_check` (prove-out / blacklist), `cfg_init`, boot counter; loader recovery mode |
| Connect | WiFi (retry every 30 s; radio cycling optional), NTP by the loader, `ip` in meta |
| Announce | one forced telemetry at boot |
| Sense | `BAT_ADC` (`batt_v`, divider 1.5 **inferred, not measured**), `CHG`, RSSI |
| Watch | VGA RGB565 diff vs the last recorded frame; heartbeat timer |
| Capture | HD RGB565 → software JPEG q85 (~160 kB), `CAPTURE_MODE = 'rgb565'` |
| Judge | not applicable on-device |
| Record | standard meta `ts seq w h v cfg ip mode why diff gate heartbeat buffered` |
| Deliver | blob gate on the LAN (plain); spool inactive (no card) |
| Report | `/telemetry` every `telemetry_s`: uptime, mem_free, boot_count, counters, diff stats, mode, cfg, batt_v, charging, rssi |
| Serve | one port; config + firmware pull every `heartbeat_s` and on refresh; push OTA kept |
| Rest | idle loop keeps the preview fresh; `wifi_linger_s` cycles the radio |
| Setup mode | as above |
| Tests | `tests/test_n6_app.py` + `cameras/common/tests` |

Proven 2026-09-03 on the bench: config pull without reflash (cfg 1 → 5),
pull OTA 2.0 → 2.0.9 in steps, rollback of a deliberately crashing 2.0.6
(reverted to 2.0.5, blacklisted, not re-pulled, 2.0.7 then installed),
setup-mode exit by viewer gone / timeout / `/live`, and radio cycling.
Not yet proven: the button (needs a hand), spool and drain (no card), a
full day of heartbeats, the battery divider (needs a meter on the pack).

## Firmware facts (5.0.0, MicroPython 1.28)

- Legacy `sensor` API works; only three framesizes (HD 1280x800, VGA
  640x400, QVGA 320x200 — 16:10) and three pixformats (RGB565, GRAYSCALE,
  BAYER at HD only). **No JPEG or YUV422 from the CSI**: capture RGB565 at
  HD and `to_jpeg()`. Framebuffer pool 32 MB, fb cost = w*h*2 for every
  format. `ssl`, `json`, `machine.LED`, `machine.Pin.board.{SW,CHG,BAT_ADC,
  LED_RED,LED_GREEN,LED_BLUE}` present; no SD slot mounted (`/sdcard` absent).
- **Drawing API differs from 4.x:** `draw_string((x, y), txt)` — the bare
  `draw_string(x, y, txt)` raises `TypeError: object 'int' isn't a tuple or
  list`; 4.x wants the opposite (`ValueError: requested length 3`). The
  shared `focus.py` tries the tuple form once and falls back.
- **`get_statistics()` fields are integers, not methods:** `st.l_stdev()`
  raises `TypeError: 'int' object isn't callable`, and the whole-number
  result is too coarse for a focus score — hence the histogram stdev.
- Deny list (hangs the MCU, bypasses rollback): `pyb.ADCAll` /
  `read_core_temp` while streaming; `sensor.set_frame_callback()`;
  `cpufreq` unproven.
- Any sub-HD BAYER framesize fails CSI init (sarg, 2026-08).
